All data is invented: the companies, LEIs, ratings, works, people and institutions. Nothing here is any rating agency's or bibliographic database's data or definitions.

Method

How the experiment is run, and the conditions it compares. The domains describe the data and the questions, the scores give the numbers, and the conclusions say what they mean for each goal.

The runs

A run asks one model every question of one dataset under several conditions, each a few times over.

  • The models: Claude Haiku and Sonnet, through the claude command line in print mode, from an empty directory with no tools, so they see only the prompt.
  • Repeats: each condition is asked five times.
  • The prompt: the data in the condition's form, then the questions, each to be answered in a sentence or two that cites the records used, and a closing JSON block that gives each answer in set fields. A run keeps its own prompts, so each one can be read on the run's page.

Grading

  • By code, against keys computed from the data. Each dataset's build script computes the key to every question from the data and its rules, and in the base datasets each key is also checked against one written by hand.
  • A checklist, for the questions that ask why. One credit question (Q6) and two research questions (Q47, Q48) ask for a reason, which code can't grade. Claude Sonnet grades them against a checklist of points, twice, so that its agreement with itself can be measured.
  • Correct, partial or wrong. An answer's JSON fields are compared with the key after normalising (ratings, yes and no, entity identifiers, counts). All fields right is correct, some right is partial, none is wrong. List answers are also scored by F1, reported beside the strict grade.
  • Accuracy is the mean over questions, with correct = 1 and partial = ½, of each question's mean over the repeats.
  • Intervals are 95% bootstrap intervals over questions. Differences between two conditions are paired, question by question, so they compare like with like.

The domains

  • Credit ratings: issuers, instruments and rating actions, with the traps of time, identity, ceilings and groups. It has three datasets: the base data, the same domain at 300 issuers, and a dataset with deep ownership chains to test whether a graph store helps with paths.
  • Research analytics: works, authors, institutions and citations, shaped like OpenAlex, with the traps of who is who, institution hierarchies, counting methods and versions. It has two datasets: the base data and the same domain at 850 works.

All the data is invented.

The ladder

Each run asks the same questions under different conditions: what the model is given, and how it gets at the data. The conditions fall into two groups:

  • Reading (R1 to R10): the model sees the rows, in the prompt, with or without their meaning in some form, and works out each answer itself.
  • Querying (D1 to D6): the model never sees the rows. It writes SQL or SPARQL, the runner executes each query and sends back the results, and the model answers from those.

Within each group, the conditions differ in how much of the data's meaning the model is given, and in what form. Each has a label, so that the pages can refer to it briefly.

Reading conditions

Condition What the model gets What it tests
R1 csv the data as CSV files the baseline
R2 rdf the same facts as RDF, no ontology what the format adds alone
R3 csv+padding the CSV plus a decoy: a glossary on the same subject (bond markets; scholarly publishing), as long as the definitions in Markdown, that defines none of the terms the questions depend on whether the gain comes from any expert text on the subject, a longer prompt full of domain words, or only from the definitions of this data
R4 csv+markdown the CSV plus the ontology's definitions as Markdown whether an ontology is just good documentation
R5 csv+ontology the CSV plus ontology.ttl: the same definitions in RDF (SKOS, in Turtle) whether writing the definitions in RDF adds anything to the same definitions as Markdown
R6 rdf+ontology the RDF data plus ontology.ttl the full knowledge-graph form: whether data and definitions in one format do better than the CSV with the definitions
R7 csv+neutral as R5 csv+ontology, with one slanted sentence made neutral (credit only) whether the wording of a single definition can change an answer
R8 csv+axioms the data plus OWL axioms and SHACL rules, with the prose taken out whether the model can use logic it has to read
R9 csv+axioms+markdown the axioms and the Markdown definitions together whether logic and prose add up
R10 executed the data after the definitions' rules have been applied in code, with no definitions: test records dropped, duplicate records merged into one entity, each rating with the period it held, ownership chains spelt out whether applying the meaning upstream, as a curated knowledge graph would, can replace telling the model what the data means

Querying conditions

The data sits either in DuckDB, an in-process SQL database, queried with SQL, or in an in-memory graph store built with rdflib, the Python library for RDF, queried with SPARQL. The model gets up to eight rounds of queries before it must answer, and a query that runs for more than 60 seconds is stopped and reported to it as failed.

The SPARQL conditions can also run on GraphDB (the free edition), a graph database built for speed. Such a run loads exactly the same triples, in a repository with no inference, so that only the engine changes; its column in the scores says GraphDB. Reproducing those runs needs a local GraphDB.

Condition What the model gets What it tests
D1 sql the raw CSV files as DuckDB tables, described by their names, columns and row counts; it queries them with SQL the querying baseline: whether a model that writes queries does better than one that reads
D2 sql+markdown the same, plus the definitions in Markdown, as R4 csv+markdown gets them whether the definitions help as much when the model writes queries as when it reads
D3 sql+executed the tables of R10 executed in DuckDB, after the rules have run: test records dropped, records merged, rating periods and ownership chains computed whether rules applied upstream make SQL reliable, with no definitions
D4 sparql the raw RDF data in a graph store, described by its prefixes, classes and properties; it queries it with SPARQL whether a graph store helps on its own, against D1 sql
D5 sparql+ontology the same, plus the definitions in Markdown, as D2 sql+markdown gets them; the ontology's triples are also loaded into the store, where queries can use them a graph with its ontology, against D2 sql+markdown: whether the store needs to be a graph
D6 sparql+axioms the graph after the SHACL rules have run, holding what they derive (on credit, one entity per LEI, ancestors and the ultimate parent; on research, one person per ORCID, credited institutions and the citations that count), with no definitions rules run in the graph, against D3 sql+executed

Read across, D1 against D4, D2 against D5 and D3 against D6 compare SQL with SPARQL given the same meaning.

What the runs cost, and how long they took

Every model call went through the claude command line in print mode, on a Claude subscription, so the runs cost nothing beyond the subscription. They did count against its usage limits, which stopped one run for about an hour.

At the API's list prices, the same calls would cost roughly $45, almost all of it Sonnet:

Sessions Input Output At list prices
Claude Sonnet 5.5 ($2 / $10 per million tokens) 593 about 15.8M tokens about 1.3M tokens about $44
Claude Haiku 5.5 ($0.10 / $0.50) 290 about 4.4M tokens about 0.5M tokens about $1

These are estimates from the saved prompts, answers and query transcripts, at about four characters a token, with each round of a querying session counted with the conversation before it. They leave out the thinking the models do before answering, which is billed as output but not saved, the grader's calls on the few questions it grades, and any saving from prompt caching. So read them as an order of magnitude.

The 36 runs on these pages ran between 4 and 6 November 2026: 883 sessions in all. Added up, the runs took about 41 hours. Since two or three ran at once, something was running for about 24 hours of those three days. A reading run on the base data takes 10 to 40 minutes, a querying run with six conditions about an hour, and the runs on the larger datasets two to four hours each.

tools/rebuild regenerates every dataset, question, key and executed table from the scripts, and every grade and report from the saved answers, in about a minute and with no model calls. tools/rebuild --check does it in a scratch copy and lists anything that differs from the repo.
