# Claude Code: project instructions

An experiment on how much an LLM gains from being told what data means. It asks the same questions over the same invented data in different forms (CSV, RDF, ontology as Turtle or Markdown, OWL and SHACL axioms, rules already executed), reading the rows or writing SQL and SPARQL over them, and grades the answers by code. Built by Michele Pasin. The repo is public at https://github.com/lambdamusic/semantic-ladder-demo (MIT), the website is at https://semantic-ladder.michelepasin.org, and Michele's blog post is at https://www.michelepasin.org/blog/2026/11/06/semantics-ladder/. It started as a clean copy of the semantics-ladder folder in `~/dev2/credit-graph-lab_2026`, which is a separate project.

Read `README.md` for what it is and the layout, `BUILDING.md` for every command (running, building, checking, the website), `notes/lab-notebook.md` (the lab notebook, a working log) for every run's findings in order, and the newest note in `backlog/log/` for where the last session stopped. Open work is in `backlog/TODO.md`, managed with the `backlog` skill, and the plan the experiment was built from is archived in `backlog/plans/000-original-plan.md`. The backlog is gitignored, so it stays local. The website's Conclusions page ends with a Future work section, the public version of the experiments still open.

## Working here

- **Python:** the virtualenv `~/Envs/semantics-ladder` (Python 3.13), created by Michele. Run everything with `~/Envs/semantics-ladder/bin/python` from the repo root: the scripts are in `src/` (`src/run.py`, `src/query.py`), a domain's build scripts in its folder. Never use `workon` or `source`. If a package is missing, add it to `requirements.txt` (pinned) and ask Michele to install it, rather than making another env.
- **Models:** called through the `claude` command line in print mode, from an empty directory with no tools (`providers.py`). This costs nothing extra, but counts against the subscription's usage limits, so don't run more than two or three runs at once. Gemini is a later, secondary step: its key goes in the `GEMINI_API_KEY` environment variable, never in a file. Opus and Gemini are set aside for now, by Michele's decision.
- **All data is invented and must stay labelled so:** the companies, LEIs, ratings, Valdoria and Corvenia, and the works, people and institutions. Don't present any of it as a rating agency's or a bibliographic database's data or definitions.
- **Git:** the repo is public, so everything committed is published. Commit as you go, and push only when Michele asks, with results committed once a run finishes. A push that changes `site/` republishes the website (`.github/workflows/pages.yml`, custom domain set in the repo's Pages settings).
- **Paths:** the macOS username is `michele.pasin`, so check every `/Users/` path.
- **Runs take time.** A reading run on a base dataset takes 10 to 40 minutes, a query run with six conditions about an hour, and runs on the larger datasets two to four hours. Run them in the background and don't edit a domain's files while a run on that domain is going. Prompts are frozen at the start of a run, but query mode reads the store's data at each session. `--resume <run>` takes the run's domain, model, conditions and questions from its folder; `--regrade` still needs `--domain`.
- **Refusals and breakdowns happen.** The API sometimes refuses a session ("safeguards flagged this message"): resume the run to ask it again. A model sometimes answers only part of the questions, or writes a SPARQL query as tool-call markup and ends with no answers. Those are kept as they are and reported, not re-asked.
- **GraphDB** (optional): Michele's local GraphDB at `localhost:7200` (free edition). Runs with `--store graphdb` use their own repository, `semantics-ladder`, cleared and loaded each session. Never touch his other repositories, such as `credit-graph` and `wed-test`.
- **Web app:** `tools/run-web` serves http://127.0.0.1:8030. Michele usually runs it himself, so don't start or stop his server. `tools/site-dump` uses its own server on port 8031 and writes `site/`; rebuild and commit `site/` when Michele asks to publish.
- **Docs are for readers who only know this repo:** the README, `BUILDING.md` and the web pages describe the experiment as it stands, not its history or what changed from the pilot before it. The lab notebook is the one place for history.

## Conventions

- Every key is computed from the data by the domain's `build_questions.py`, and checked against a key written by hand in the base domains. Never edit `questions.json` by hand. When a key is found wrong, fix the rule, rebuild the questions, write the new key into the affected runs' own `questions.json`, and regrade them.
- Each run folder keeps its own `questions.json`, prompts and `meta.json` (with the commit). Regrading (`src/run.py --domain <d> --regrade <run>`) uses the run's own questions, because keys change when a domain does.
- After changing a domain, the grading or the report format, run `tools/rebuild --check`: it rebuilds every dataset and regrades every run in a scratch copy of the last commit, and should report that it matches file for file.
- A domain's meaning lives in `ontology/ontology.ttl`, beside `axioms.ttl` (checked against the keys by the domain's `check_axioms.py`) and the decoy `padding.md`. `ontology.md` is generated from it by `src/ontology_to_md.py`, and must never be edited by hand. The scaled copies (`credit_300`, `credit_paths`, `research_850`) get their ontology files copied by the build script, so don't regenerate theirs: they have no converter, and the column names would drop out. `data/inferred.ttl`, the graph after the SHACL rules, is a cache, gitignored and rebuilt on demand.
- The web pages' text lives in `docs/`: `docs/goals.md`, `method.md`, `scores.md` and `conclusions.md`, and `docs/<dataset>/<section>.md` (a dataset's `scores.md` goes under its table on the scores page). The numbers in a page's text don't update themselves, but the tables do: one column per model, mode and store, filled from the latest runs on the current questions. Conditions a dataset leaves out on purpose are listed in `LEFT_OUT` in `src/web/apps/lab/files.py`.
- Score cells on the Scores and Conclusions pages are shaded by `src/web/static/js/site.js`, from any table cell holding one percentage. Keep scores written as "84%" in the docs' tables so they shade.
